Section 1

RAG Foundations

15 min

Framing section — the whole pipeline is greyed out here because we're zooming out. Goal: everyone agrees on what RAG is, why standalone LLMs are insufficient, and where in the pipeline failures live. 15 min, keep moving.

What is RAG? WHY

Retrieval-Augmented Generation = a retriever + a generator.

  • Retriever: fetch the most relevant chunks from your knowledge base.
  • Generator (LLM): answer the question grounded in those chunks.
  • The LLM is no longer answering from memory — it answers from evidence you supply.
Mental model: open-book exam. The LLM is smart but forgetful — RAG hands it the right page at the right moment.
Anchor on the open-book exam metaphor — students remember it. The retriever chooses which page; the generator writes the answer using that page. Everything else today is about making the retriever pick the RIGHT page and making the generator actually USE it and not wander off.

Why not just use a bigger LLM? WHY

Standalone LLM limitations:

  • 🕰️ Stale knowledge — frozen at training cutoff.
  • 🌀 Hallucination — fluent, confident, wrong.
  • 🔗 No citations — you can't verify or audit the answer.
  • 🔒 No private data — it never saw your internal docs.
RAG targets all four: fresh + grounded + citable + private.
These four are the business case for RAG. Give a one-liner example each: stale = "who won last quarter"; hallucination = made-up API endpoint; citations = compliance/legal need the source; private = your Acme Cloud SLA doc is not on the public web. Ask the room which of these bites them most at work.

The modular pipeline WHAT

StageJob
LoadingIngest raw sources into clean documents + metadata
ChunkingSplit documents into retrievable units
RetrievalFind the most relevant chunks for a query
AugmentationInject chunks into the prompt (context assembly)
GenerationLLM produces a grounded, cited answer
EvaluationMeasure quality, diagnose which stage failed
This is the table version of the diagram. The key insight: these are SEPARABLE concerns you can test and swap independently. That modularity is exactly what lets us debug — we can point at one stage. Note augmentation vs generation are distinct (we treat them together timing-wise but they are different jobs).

End-to-end example flow WHAT

Query: "Does Acme Cloud offer a 99.99% SLA?"

  1. Load Acme SLA + pricing docs → clean text + metadata.
  2. Chunk the SLA doc into ~300-token passages.
  3. Retrieve top passages by similarity to the query.
  4. Augment — build a prompt: system rules + retrieved passages + question.
  5. Generate — "Yes, the Enterprise tier offers 99.99% [SLA §2.1]."
  6. Evaluate — is it faithful? did we retrieve the right §?

The Acme Cloud fictional corpus (pricing, security, SLA, API, onboarding, FAQ) is what every notebook uses, so this exact query returns throughout the day. Notebook 01 introduces it; Notebook 08 wires it end-to-end.

Where do failures occur? WHY

Recurring question of the day: "What happens if THIS step is poorly designed?"

StageIf poorly designed…
LoadingGarbled text, lost tables, no metadata → nothing downstream can recover it
ChunkingIdeas split or diluted → retriever can't match them
RetrievalWrong chunks surface → the LLM is grounded in the wrong evidence
AugmentationContext truncated / mis-ordered → key fact never reaches the model
GenerationWeak prompt → model ignores context, hallucinates anyway
EvaluationNo metrics → you ship bugs blindly, can't tell which stage broke
Errors compound: bad chunking → poor retrieval → bad answer. Fix the earliest broken stage first.
This is the thesis slide of the whole session — spend a full minute. Every later section returns to its row here. Emphasise compounding: a 90% accurate stage times a 90% stage times a 90% stage is already ~73%. And a downstream stage CANNOT fix an upstream defect — if loading dropped a table, no reranker brings it back. This is why we debug earliest-stage-first.

Section 2

Loading

15 min

Light up Loading. This is the least glamorous, most under-invested stage — and it silently determines the ceiling of everything else. 15 min. Predict-before-run reminder: before we run the loader on a PDF, ask the class what they think happens to the tables and footers.

Why ingestion matters WHY

  • Loading is the front door — everything downstream sees only what you let in.
  • The retriever can only find what was ingested cleanly and preserved.
What happens if loading is poorly designed? Garbled encoding, merged columns, dropped tables, and lost structure become permanent — no downstream stage can recover deleted information.
Cause → effect: raw PDF dump → headers/footers pollute chunks → retriever matches noise → wrong answer.
Drive home irreversibility. If a table becomes a wall of numbers with no rows, the meaning is gone before chunking even starts. Ask: "what happens if this step is poorly designed?" — answer: you cap the quality of the entire system and you can't tell later, because the text still LOOKS fine.

Formats & sources WHAT

Sources

  • 📄 PDF — layout, tables, columns
  • 🌐 HTML — nav/ads/boilerplate noise
  • 📝 Markdown — structure is a gift (headings!)
  • 🔌 APIs / DBs — JSON, tickets, records

Each needs care

  • PDF → extract text order, keep tables
  • HTML → strip chrome, keep main content
  • MD → use headings as natural boundaries
  • API → flatten + attach source metadata

Every format is a different extraction problem — there is no universal loader.

The point: "load a document" is deceptively simple. HTML is mostly boilerplate you must remove; PDFs reorder text and murder tables; Markdown hands you structure for free. Loaders in our package handle these per-format. Tell them: the effort you invest per format pays off at retrieval time.

Do's & Don'ts WHAT

✅ Do

  • Clean text (whitespace, encoding, hyphenation)
  • Preserve structure — headings, lists, tables
  • Attach metadata: source, title, section, date, URL
  • Normalise unicode; fix mojibake early

❌ Don't

  • Dump raw bytes / raw PDF text blindly
  • Ignore encoding → � garbage in embeddings
  • Keep nav bars, cookie banners, page numbers
  • Throw away the source → no citations later
Metadata is not optional: it powers filtering (retrieval) and citations (generation).
Single most important do: KEEP METADATA. Source + section is what makes "[SLA §2.1]" citations possible two stages later, and what enables metadata filtering in retrieval. Failure mode to name: the "raw dump" anti-pattern where people str() a PDF and move on — it feels done but poisons everything.

Section 3

Chunking

20 min

Chunking box lit. This is where most "why is my RAG bad?" problems are actually born, and it's the most under-appreciated. 20 min. We will compare chunk strategies side by side — set that expectation now.

The chunking problem WHY

  • We can't embed or retrieve a whole 40-page doc — too big, too diffuse.
  • We must split it into units small enough to embed, big enough to mean something.
  • The chunk is the atomic unit of retrieval — you retrieve chunks, not documents.
What happens if chunking is poorly designed? The right answer may be split across two chunks (so neither matches), or buried in a huge chunk (so its embedding is diluted). Retrieval then cannot win — the ceiling is set here.
Reframe: a chunk is what gets embedded and retrieved. If a fact and its context land in different chunks, the retriever sees half-truths. If a chunk is a whole page, its single embedding vector is an average of ten topics — it matches everything weakly and nothing strongly. This is the cause of "retrieval looks fine but answers are vague."

Strategies WHAT

StrategyHowTrade-off
Fixed-sizeEvery N tokens/chars, blindSimple, fast · cuts mid-sentence
RecursiveSplit on ¶ → sentence → word, respecting separatorsGreat default · respects structure
SemanticSplit where embedding similarity drops (topic shift)Best boundaries · slower, costlier
Rule of thumb: start with recursive; reach for semantic when boundaries really matter and budget allows.
Fixed = naive baseline; useful to show WHY it hurts. Recursive is the workhorse — it tries paragraph breaks first, only cutting finer when a piece is still too big, so it preserves natural structure. Semantic is the sophisticated option: embed sentences, cut where topic shifts — expensive but boundary-aware. Tell them 90% of projects live on recursive.

Chunk size vs overlap WHAT

Size

  • Too large → embedding is an average → diluted, matches weakly
  • Too small → idea fragmented → missing context to answer
  • Sweet spot: usually ~200–500 tokens (data-dependent)

Overlap

  • Repeat a slice between neighbours (~10–20%)
  • Stops facts being cut exactly at a boundary
  • Too much → duplicate hits, wasted context budget
🔮 Predict: for our Acme SLA, will 128-token or 512-token chunks retrieve the "99.99%" clause better? Why?
This is the central chunking trade-off — draw it as a dial. Large chunks: one vector summarising many ideas, low precision. Small chunks: precise but context-starved, the model gets a fragment it can't reason over. Overlap is the safety net against boundary cuts. Have them predict before Notebook 03 runs the comparison.

Do's & Don'ts WHAT

✅ Do

  • Preserve semantic boundaries (paragraphs, sections)
  • Keep heading/section in chunk metadata
  • Tune size to your content & embedding model
  • Add modest overlap

❌ Don't

  • Cut mid-sentence / mid-table
  • Make chunks so large the embedding is diluted
  • Make chunks so small ideas fragment
  • Use one size for every document type
Cause → effect: bad chunking → poor retrieval → bad answer. The whole chain starts here.
Reinforce the flagship cause→effect chain. The don'ts map directly to failure modes we'll see in evaluation: fragmented ideas → low recall; diluted embeddings → low precision. Emphasise "one size fits all" is a real anti-pattern — an API reference chunks very differently from prose FAQ.

Section 4

Retrieval

30 min

Retrieval lit — the heart of RAG, 30 min. This is where "just use cosine top-k" quietly fails and where hybrid + reranking earn their keep. Big theme: retrieve WIDE, rerank NARROW.

Why retrieval is the crux WHY

  • The generator can only be as good as the evidence it's given.
  • Retrieval decides which evidence — the single highest-leverage stage.
What happens if retrieval is poorly designed? You feed the LLM the wrong or incomplete chunks. It then either hallucinates or confidently answers from irrelevant context — "garbage in, grounded garbage out."
"An LLM given the right paragraph rarely fails. An LLM given the wrong paragraph rarely succeeds."
Set stakes: most RAG debugging ends here. If you retrieve the wrong chunk, no prompt engineering saves you. Conversely, great retrieval makes an average LLM look brilliant. This is why we spend 30 minutes and why evaluation later separates retrieval metrics from generation metrics.

Embeddings & similarity WHAT

  • An embedding maps text → a vector; similar meaning → nearby vectors.
  • Cosine similarity = angle between query & chunk vectors (1 = identical direction).
  • Retrieval = embed the query, find nearest chunk vectors.
from rag_pipeline.embeddings import embed
import numpy as np
def cosine(a,b): return a@b/(np.linalg.norm(a)*np.linalg.norm(b))
q = embed("Does Acme offer a 99.99% SLA?")
scores = [(cosine(q, embed(c)), c) for c in chunks]   # rank desc

→ Notebook 04 · embeddings.py (text-embedding-3-small default)

Keep the math intuitive: meaning becomes geometry; retrieval becomes "find nearby points." Cosine ignores magnitude, compares direction. Mention the model: text-embedding-3-small by default, with an offline mock fallback so the notebook runs without keys. Predict: which Acme chunk scores highest for the SLA query?

Vector stores (conceptual) WHAT

  • A vector store indexes millions of chunk vectors for fast nearest-neighbour search (ANN).
  • You don't compare against every vector — the index prunes the search.
  • Stores metadata alongside vectors → enables filtering.
  • Examples: FAISS, Chroma, pgvector, Pinecone, Weaviate (we use a simple in-memory store).

→ vectorstore.py (add, search, filter)

Conceptual only — don't rabbit-hole on ANN algorithms. The idea: a searchable index of vectors + their metadata. Our package ships a tiny in-memory store so the mechanics are visible; in production you'd swap in FAISS/Chroma/pgvector. The store also holds metadata, which sets up filtering two slides on.

Dense retrieval & its blind spot WHAT

Dense (semantic)

  • Embedding similarity
  • Great at meaning / paraphrase
  • "cost" ≈ "pricing" ✅

Blind spot

  • Misses exact keywords, IDs, codes
  • "SKU-4471", "§2.1", rare terms
  • Vector for a rare token is weak
This is exactly what keyword (BM25) retrieval is good at → motivates hybrid.
Dense retrieval's superpower (semantics) is also its weakness (exact terms). Rare identifiers, part numbers, legal section refs — embeddings smear these. That's the setup for hybrid: pair dense with BM25 keyword search so you get both meaning AND exact match. Predict: which method finds "§2.1" better?

Hybrid search: BM25 + dense WHAT

  • BM25 — classic sparse keyword scoring (exact terms, TF-IDF family).
  • Dense — semantic similarity.
  • Fuse the two ranked lists with Reciprocal Rank Fusion (RRF):
# RRF: rank-based, score-scale agnostic
def rrf(rankings, k=60):
    fused = {}
    for ranked in rankings:                 # each is a list of doc_ids best->worst
        for rank, doc_id in enumerate(ranked):
            fused[doc_id] = fused.get(doc_id, 0) + 1/(k + rank + 1)
    return sorted(fused, key=fused.get, reverse=True)

from rag_pipeline.retrieval import HybridRetriever   # BM25 + dense, RRF inside

→ Notebook 04 · retrieval.py (DenseRetriever, BM25Retriever, HybridRetriever)

Why RRF and not "average the scores": BM25 and cosine live on totally different scales — averaging is meaningless. RRF only uses RANK position, so it fuses fairly. A doc ranked high by either method bubbles up; agreement compounds. This is the single most practical retrieval upgrade over naive top-k.

Metadata filtering WHAT

  • Constrain the search space before similarity: source="SLA", date>2025, tier="Enterprise".
  • Turns "search everything" into "search the right shelf."
  • Cheap, huge precision win — this is why we kept metadata at loading.
results = store.search(q, k=20, where={"source": "acme_sla"})
Callback: metadata you preserved in Stage 1 pays off here in Stage 3.
Explicitly connect back to loading — this is the payoff for keeping metadata. Filtering removes obviously irrelevant candidates so similarity works on a clean set. Example: a question about Enterprise pricing shouldn't retrieve Free-tier chunks. Cheap and powerful.

Reranking: retrieve wide, rerank narrow WHAT

  • First-stage retrieval is fast but coarse → pull a wide candidate set (k=50).
  • A reranker scores each candidate against the query more precisely → keep top 5.
  • Cross-encoder: query+chunk through one model → accurate, slower.
  • LLM reranker: ask an LLM to rank — pointwise (score each) or pairwise (compare pairs).
from rag_pipeline.retrieval import CrossEncoderReranker, LLMReranker
cands = hybrid.retrieve(q, k=50)          # wide
top   = CrossEncoderReranker().rerank(q, cands, k=5)   # narrow

→ Notebook 04 · CrossEncoderReranker, LLMReranker

The mantra of the section: RETRIEVE WIDE, RERANK NARROW. Bi-encoder (embeddings) is fast because query and doc are encoded separately; a cross-encoder reads them TOGETHER, so it's far more accurate but too slow to run on the whole corpus — perfect as a second stage on 50 candidates. LLM rerankers: pointwise scores each doc, pairwise compares two at a time (more accurate, more calls).

Do's & Don'ts WHAT

✅ Do

  • Optimise recall first, then precision
  • Retrieve wide → rerank narrow
  • Combine dense + BM25 (hybrid)
  • Use metadata filters

❌ Don't

  • Rely only on top-k cosine similarity
  • Set k too small (miss the answer entirely)
  • Ignore exact-match / keyword queries
  • Skip reranking on high-stakes queries
Recall then precision: first make sure the answer is somewhere in your candidates (recall); then push it to the top (precision, via reranking).
Explain the ordering: if the right chunk isn't even in your candidate set, no reranker can save you — that's a recall failure, fix k / hybrid / filters. Once it's IN the set, reranking is a precision problem. The cardinal sin is "top-3 cosine and ship it." Predict-then-run: compare dense-only vs hybrid vs hybrid+rerank on a tricky Acme query in Notebook 04.

Section 5

Augmentation & Generation

40 min

Two boxes in play — augmentation (assembling context) then generation (the LLM answering). Diagram lights augmentation now; we'll flip to generation mid-section. 40 min, the biggest block. Core message: retrieval found the evidence; augmentation decides HOW it reaches the model, and generation decides whether the model USES it faithfully.

Augmentation ≠ Retrieval WHAT

RetrievalAugmentation
QuestionWhich chunks?How do they enter the prompt?
OutputRanked chunksThe final assembled prompt
FailureWrong evidenceRight evidence, badly presented / truncated
What happens if augmentation is poorly designed? You retrieved the perfect chunk, then buried it, truncated it, or ordered it so the model overlooks it. Great retrieval, wasted.
Students conflate these constantly. Retrieval = selection. Augmentation = presentation/assembly: ordering, formatting, de-duping, fitting the context window, keeping source labels. A perfect retrieval can still be ruined by dumping 50 chunks in random order and blowing the token budget.

The context-injection problem WHY

  • Context windows are finite — you can't stuff everything.
  • Order matters: models attend unevenly ("lost in the middle").
  • Too much context → noise, cost, latency; too little → missing the answer.
How you inject the chunks is itself a design decision — enter stuffing / map-reduce / refine.
Name "lost in the middle" — models recall the start and end of a long context better than the middle, so put the strongest chunk first or last. The injection strategy is a real fork in the road, not an implementation detail. Set up the next three slides.

Injection strategies WHAT

StrategyHowWhen
StuffingConcatenate all chunks into one promptFew chunks, fits window — the default
Map-ReduceAnswer per chunk (map) → combine (reduce)Many chunks, parallel, scalable
RefineDraft, then iteratively improve with each chunkLong-form, quality > latency
🔮 Predict: for a question answered by ONE Acme paragraph — which strategy is best on cost and quality? What about a question spanning 8 docs?

→ Notebook 05 · augmentation.py (stuff / map_reduce / refine)

Stuffing: simplest, one call, but breaks when context overflows. Map-reduce: scales to many docs, parallel calls, but loses cross-chunk context and costs N calls. Refine: highest quality on synthesis tasks, sequential and slow. Trade-off is cost/latency vs completeness. Have them predict before Notebook 05 runs all three.

Return sources with the answer WHAT

  • Every claim should carry its citation back to a chunk's metadata.
  • Enables verification, trust, debugging, compliance.
  • Recall: only possible because we preserved metadata at loading.
answer = {
  "text": "Enterprise tier includes a 99.99% uptime SLA.",
  "sources": [{"source": "acme_sla", "section": "2.1", "score": 0.88}]
}
A RAG answer without sources is just a hallucination you happen to trust.
Non-negotiable in production: carry sources through. It's the difference between an auditable system and a confident guess. It also supercharges debugging — when an answer is wrong you immediately see WHICH chunk misled it, telling you whether to blame retrieval or generation. Third callback to loading-stage metadata.

Generation: the LLM's role WHAT · GEN

  • The LLM synthesises an answer from provided context — it should not add outside facts.
  • Its job: read evidence, reason, write grounded prose, cite.
  • Model choice matters far less than the evidence + prompt you give it.
Flip the diagram to Generation now. Reframe the LLM's role: not "the brain that knows things" but "the reasoner over evidence you supplied." This is the setup for the takeaway — swapping GPT for Claude helps far less than fixing chunking/retrieval. Default model gpt-4o-mini; Claude adapter available; mock fallback.

Prompt design with context WHAT

SYSTEM = """You are a support assistant for Acme Cloud.
Answer ONLY using the context below. Cite sources as [source §section].
If the context is insufficient, reply exactly: "I don't know based on the provided documents."
Do not use outside knowledge."""

prompt = f"{SYSTEM}\n\n# Context\n{numbered_chunks}\n\n# Question\n{query}"
  • Explicit instruction to ground; explicit citation format.
  • Explicit escape hatch: allow "I don't know."

→ Notebook 05 · generation.py (grounded prompts + citations)

Walk each line: "ONLY using context" fights hallucination; the citation format makes sources verifiable; the "I don't know" clause is the single highest-ROI line — it gives the model permission to abstain instead of inventing. Numbering chunks lets it cite by index. This is prompt design as a pipeline stage, not an afterthought.

Augmentation & generation failure modes WHY

  • 🌀 Hallucination despite context — model ignores evidence, uses training memory.
  • ✂️ Context overflow — the key chunk truncated out of the window.
  • 🔇 Lost in the middle — right chunk present but positionally ignored.
  • 🎭 Over-confidence — no "I don't know", so it fabricates when unsure.
  • 🧾 Uncited claims — can't trace or verify.
What happens if generation is poorly designed? The model wanders off the evidence — the one thing RAG existed to prevent.
Each of these maps to a fix on the next slide. The subtle one: hallucination WITH good context — the model pattern-completes from training instead of reading. Weak prompts cause it. This is why grounding instructions and abstention aren't optional polish; they're the mechanism.

Safe prompt engineering HOW

✅ Techniques

  • Instruction prompts ("use only context")
  • Require citations per claim
  • Grounding + abstention: "answer 'I don't know' if context insufficient"
  • Number chunks; put strongest first/last

❌ Avoid

  • Open-ended "answer the question"
  • No source constraint
  • No abstention path → forced to guess
  • Dumping unordered chunks
🔮 Compare: same query, same chunks — with vs without the grounding prompt. Watch the hallucination appear/disappear.
Run the with/without comparison live — it's the most memorable moment of the section. Feed an unanswerable question: the naive prompt fabricates; the grounded prompt says "I don't know." Same model, same context — the ONLY difference is prompt design. This proves generation is a design decision.

Section 6

Evaluation

35 min

Evaluation lit — note it loops back to earlier stages. 35 min. Message: you cannot improve what you don't measure, and crucially, evaluation tells you WHICH stage to fix. Without it you tune randomly.

Why evaluate? WHY

  • RAG has many moving parts — "it feels better" is not a metric.
  • Evaluation localises failure: retrieval vs generation vs chunking.
  • It's the feedback loop that closes the pipeline.
What happens if evaluation is poorly designed (or skipped)? You ship regressions blindly, tune the wrong stage, and can't tell if a change helped or hurt.
The unsexy stage that makes all the others improvable. Emphasise localisation: a low context-precision points at retrieval/chunking; a low faithfulness with good context points at generation. Evaluation turns "my RAG is bad" into "my retrieval recall@5 is 0.4, fix chunking."

Failure modes to measure WHAT

  • 🎯 Retrieval errors — right chunk missing or ranked low.
  • 🌀 Hallucination — claims not supported by context.
  • 🌫️ Context noise — irrelevant chunks dilute the answer.
Each failure mode has a different metric — and points at a different stage to fix.
Tie each failure to a stage: retrieval errors → retrieval/chunking; hallucination → generation prompt; context noise → retrieval precision / reranking. This mapping is the diagnostic skeleton we'll formalise with metrics next.

Latency & cost breakdown WHAT

StageLatencyCost driver
Embed querylowembedding call
Vector searchlowindex size
Rerank (cross-enc / LLM)med–high#candidates × model
Generationhighinput tokens (context!) + output
More context → better grounding but more tokens = more cost + latency. Quality is a budget.
Make it real: generation input tokens dominate cost, and context IS input tokens — so stuffing 50 chunks is a cost decision, not just a quality one. Reranking adds latency proportional to candidate count. Good RAG engineering is Pareto: maximise faithfulness per dollar and per second, not in the abstract.

Answer-quality metrics WHAT

  • Relevance — does the answer address the question?
  • Faithfulness — is every claim supported by the retrieved context? (anti-hallucination)
  • Context precision — of retrieved chunks, how many are relevant?
  • Context recall — of the relevant chunks, how many did we retrieve?
Faithfulness answers "did it make things up?" Context precision/recall answer "did retrieval do its job?"
Distinguish clearly: faithfulness is a GENERATION metric (grounded in given context, regardless of whether context was right); context precision/recall are RETRIEVAL metrics. A faithful answer to bad context is still wrong — you need both. This separation is what lets you localise the bug.

Retrieval metrics WHAT

  • Precision@k — fraction of top-k that are relevant.
  • Recall@k — fraction of all relevant items found in top-k.
  • MRR — Mean Reciprocal Rank: 1/rank of the first relevant hit.
from rag_pipeline.evaluation import precision_at_k, recall_at_k, mrr
precision_at_k(retrieved, relevant, k=5)
recall_at_k(retrieved, relevant, k=5)
mrr(retrieved, relevant)

→ Notebook 06 · evaluation.py

Intuition: precision@k = "is my top-k clean?"; recall@k = "did I miss the answer?"; MRR = "how high is the first good hit?" MRR rewards putting the right chunk at rank 1 — directly the payoff of reranking. These need ground-truth relevance labels, which motivates the eval-dataset slide.

RAGAS framework WHAT

  • Automated, LLM-assisted RAG evaluation — no giant hand-labelled set required.
  • Key metrics: faithfulness, answer correctness, context utilisation (+ relevancy, precision/recall).
  • An LLM judges whether claims are grounded and whether context was used.
from rag_pipeline.evaluation import ragas_evaluate
scores = ragas_evaluate(questions, answers, contexts, ground_truths)
# -> {'faithfulness':0.82, 'answer_correctness':0.75, 'context_utilisation':0.68}

→ Notebook 06 · RAGAS wrapper

Limits: the judge is itself an LLM — noisy, biased, costs money. Automation scales; it does not replace human spot-checks.
RAGAS lets you score without labelling everything by hand — great for scale and regression testing. But be honest about limits: an LLM judge has variance and bias, and can be gamed. Use it for trend/regression detection, and keep human review on high-stakes samples. Automated vs manual is a spectrum, not either/or.

Manual vs automated evaluation WHAT

Manual

  • Human reads answers, rubric-scores
  • High trust, catches nuance
  • Slow, doesn't scale, subjective

Automated (metrics + RAGAS)

  • Fast, repeatable, CI-friendly
  • Scales to thousands of queries
  • Noisy; judge can be wrong
Practice: automate the bulk, manually audit a stratified sample and every regression.
The mature answer is "both, layered." Automated metrics run in CI on every change; humans audit a representative sample and investigate anything that moves. Neither alone is sufficient — automation without spot-checks drifts; manual-only doesn't scale.

  • Negative testing — questions your corpus cannot answer → the system must say "I don't know."
  • Metrics vs rubrics — numeric scores (automatable) vs qualitative criteria (human judgement).
  • Cover the distribution: easy, multi-hop, exact-term, out-of-scope.

Diagnose a bad RAG output HOW

Q: "What's Acme's data-residency guarantee for EU customers?"

A: "Acme stores all EU data in Frankfurt with a 100% residency guarantee." ❌ (fabricated)

StageCheckVerdict
LoadingWas the security doc ingested?✅ present
ChunkingIs residency clause intact in one chunk?⚠️ split across two
RetrievalDid the residency chunk rank top-k?❌ recall@5 miss
AugmentationWas it in the prompt?❌ never retrieved
GenerationDid it abstain?❌ no "I don't know"
Root cause = chunking split → retrieval miss. Amplified by no abstention. Fix earliest first.
This is the pipeline-thinking payoff. Walk each stage as a checklist. Notice TWO defects: an upstream cause (chunk split → not retrieved) and a downstream amplifier (no abstention → it guessed). The discipline: fix the EARLIEST broken stage first (chunking), because fixing generation alone would just make it abstain, not answer correctly. RAGTrace in pipeline.py exposes exactly this per-stage view.

Explore Advanced RAG

Naïve vs Advanced vs Modular WHAT

ParadigmIdea
NaïveLoad → chunk → embed → top-k → stuff → generate. Linear.
AdvancedAdd pre-retrieval (query rewriting) & post-retrieval (reranking, compression).
ModularSwappable, routed, iterative components — retrieve multiple times, branch, loop.
We built the modular mindset all day — that's why upgrading one stage doesn't break the rest.
Position today's work: we taught the pipeline modularly precisely so these advanced patterns are just stage swaps. Naive is the baseline; advanced adds pre/post-retrieval polish; modular makes the flow itself programmable (routing, loops). Everything below is an instance of these.

Agentic & multi-hop RAG WHAT

  • Agentic RAG — the LLM decides when and what to retrieve, using tools. (agents not covered yet — mention only)
  • Tool-augmented retrieval — calculators, search, APIs alongside the vector store.
  • Multi-hop RAG — answer needs chained lookups (A → B → C).
  • Query decomposition — split a complex question into sub-questions, retrieve each.
More power, more failure surface, more latency/cost — reach for it only when the task demands it.
Flag agentic as a forward reference — we cover agents in a later module, so this is awareness only. Multi-hop: "which region hosts the tier that includes 99.99% SLA?" needs two retrievals. Query decomposition is the practical technique. Caution: each hop compounds error and latency.

Structured data & Graph RAG WHAT

  • Not all knowledge is prose — SQL databases, tables, knowledge graphs.
  • Text-to-SQL RAG — retrieve by generating a query over structured data.
  • Graph RAG — retrieve over a knowledge graph: entities + relationships, traverse edges for multi-hop reasoning.
  • Better for connected facts, aggregations, "how are X and Y related?"
Vector search is weak at aggregation ("how many enterprise customers?") and relationships. Graph RAG encodes entities and edges, so multi-hop relational questions become graph traversals — far more reliable than hoping cosine similarity chains the facts. Text-to-SQL handles precise structured lookups. Awareness level; students should know these exist for connected/structured data.

Adaptive retrieval & trends WHAT

  • Dynamic k — retrieve more/fewer chunks based on query difficulty.
  • Query rewriting — clean/expand the query before retrieval.
  • Long-context models vs RAG — bigger windows don't kill RAG (cost, freshness, citations still win).
  • Caching — cache embeddings, retrievals, even generations to cut cost/latency.
When to go beyond basic RAG: only when metrics show a ceiling — measure first, then add complexity to the specific stage that's limiting.
Address the "won't long context replace RAG?" question head-on: no — you still need freshness, private data, citations, and cost control; stuffing a whole corpus every call is expensive and noisy. Guidance: don't add complexity speculatively; let evaluation tell you which stage is the bottleneck, then upgrade that stage. Caching is the cheapest real-world win.

The debugging workflow HOW

  1. Reproduce the bad answer; capture the RAGTrace.
  2. Walk stages in order: was the doc loaded? chunk intact? retrieved? in the prompt? did it abstain?
  3. Find the earliest broken stage — that's the root cause.
  4. Fix it; re-run the eval set (incl. negatives) to confirm no regression.
Don't tune the LLM first. Follow the pipeline; fix earliest-broken-first.
Give them a repeatable procedure, not vibes. The instinct is to swap models or fiddle the prompt; the discipline is to trace stage by stage and fix the earliest defect, because downstream can't repair upstream. Always re-run the eval set — including negative tests — so a fix doesn't silently break abstention.

The one takeaway

RAG performance is determined by cumulative design decisions across ALL stages — not just the choice of LLM.

Loading · Chunking · Retrieval · Augmentation · Generation · Evaluation
